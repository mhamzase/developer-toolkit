# Zase Website

The website lives in `site/` inside this repo, next to the extension.
It is a fully static site generated by `site/build.mjs` (Node, zero
dependencies) and deployed with Cloudflare Pages. The extension and
the website share one source of truth: the site loads the tool
registry from the real files in `js/tools/`, so a tool added to the
extension appears on the website at the next build, with no separate
tool list to maintain.

## How it works

- `site/build.mjs` loads every tool file in a Node vm sandbox (the
  same approach as `tests/smoke.js`), reads the registered metadata
  (name, category, icon, description, keywords), and renders:
  - `dist/index.html`: home page with hero, live search, and all
    tools grouped by category.
  - `dist/<slug>/index.html`: one page per tool. Slugs are
    search-friendly (`json` becomes `json-formatter`); the map lives
    at the top of `build.mjs`. A tool missing from the map falls back
    to its id and the build prints a warning.
  - `dist/about/`, `dist/privacy/`, `dist/404.html`,
    `dist/sitemap.xml`, `dist/robots.txt`.
- It also copies the extension runtime files the tools need into
  `dist/` with their repo paths preserved (`js/`, `css/`, `assets/`),
  which keeps relative URLs inside the CSS (fonts) working.
- Each tool page loads only the shared runtime (all of `js/utils/`,
  `js/core/storage.js` + `session.js` + `registry.js`, and the
  `js/ui/` panel kit: dom, panel, toast, dl-button, filedrop) plus
  that page's own tool file. Popup-shell-only UI (sidebar, grid,
  settings, router, and friends) is not part of the website.
- `site/src/assets/web-shim.js` provides the small slice of Chrome
  APIs the tools were written against (`chrome.storage.local` backed
  by localStorage, `chrome.storage.onChanged` no-op,
  `chrome.runtime.getManifest()`), so the unmodified extension
  scripts run on the web. The build injects the real manifest name
  and version into the shim.
- `site/src/assets/web-boot.js` mounts the page's single tool;
  `site/src/assets/site.js` handles the dark/light toggle (stored in
  localStorage, OS preference by default) and the home search filter.
- `site/dist/` is generated output: it is gitignored and never
  committed. Cloudflare Pages builds it from source on every deploy.

## Local build and preview

```bash
node site/build.mjs
```

Then serve `site/dist/` with any static server, for example:

```bash
npx serve site/dist
# or
python3 -m http.server 8000 --directory site/dist
```

## Cloudflare Pages settings

Create the project once in the Cloudflare dashboard (Pages, Create,
Connect to Git, pick this repo):

| Setting | Value |
|---|---|
| Project name | devtoolkit-zase (gives devtoolkit-zase.pages.dev) |
| Production branch | dev |
| Root directory | repo root (leave empty / `/`) |
| Build command | `node site/build.mjs` |
| Build output directory | `site/dist` |
| Framework preset | None |

Notes:

- All website work happens on the `dev` branch, and the production
  site updates on every push to `dev`. On the day the owner orders
  the `dev` to `master` merge, switch the production branch above
  to `master` in the same settings screen.
- A custom domain can be attached later in the same dashboard
  (Pages project, Custom domains) with no code changes; canonical
  URLs in the build point at `https://devtoolkit-zase.pages.dev` and
  would be updated in `site/build.mjs` (the `BASE_URL` constant) if
  the domain changes.

## Extension packaging stays separate

The store zip is built by `scripts/package-extension.mjs` from a
fixed whitelist only (`manifest.json`, `background.js`, `LICENSE`,
`popup/`, `js/`, `css/`, `assets/`):

```bash
node scripts/package-extension.mjs
# writes ~/workspace/developer-toolkit-v<version>.zip
```

The script verifies its own output and fails if any non-whitelist
entry gets in, so the website can never leak into the store package.
